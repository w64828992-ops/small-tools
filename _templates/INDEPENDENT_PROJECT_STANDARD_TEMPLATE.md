# 独立软件仓库规则编制模板

模板依据：Routing Standard v1.0.0。
使用方式：按实际需求填写并拆分为项目内的文档；未决项明确写待确认。不要整份照抄、保留无关章节或把模板当成已完成验收。

## 项目立项与分仓

- 软件名称、目标用户、用途和业务问题：
- 范围与明确不做的内容：
- 规模判断、独立建仓依据、是否已有同名/同用途仓库：
- Repository（owner/name）、本地长期路径、默认可见性：
- 技术栈选择依据、维护周期、安全级别及待确认事项：
- 阶段目标、验收场景和可测量标准：

## README.md 与 AGENTS.md

README 说明真实用途、范围、当前状态、版本来源、安装/启动/构建、配置、依赖、示例、测试、限制和各规范入口。无真实应用或未执行操作如实标记，不虚构已发布版本。

AGENTS 指向本项目唯一主规则，固定已确认的仓库和路径，要求检查工作区、使用临时分支、中文注释、适用测试及扫描，并依据任务授权完成 PR/CI/归档。明确越权、业务变更、失败与破坏性操作的暂停条件。

## docs/REPO_STANDARD.md

填写项目自己的 Rule Version、生效日期、适用范围、规则来源与取舍、主规则优先级、目录约定、开发流程、文档要求、版本/Tag、测试/CI、权限、评审、发布/回滚及完成定义。

独立单产品不要强制“一级目录都必须有独立 VERSION”，不默认建立 tool/* 或 develop。多组件需要独立版本时明确版本源、依赖兼容和联动发布规则。主规则升级同步检查器、模板和入口。

## docs/DEVELOPMENT_STANDARD.md

写明已选语言及版本、命名、模块边界、依赖和锁文件、错误处理、接口约束、日志、格式、代码审查及对应工具命令。只保留可执行的构建和验证入口。

中文注释为硬性要求：所有自行维护文件说明用途，类、具名函数和方法说明职责，核心计算、权限、数据修改与异常边界说明设计原因和维护风险。注释随代码更新，测试说明验证场景。标识符和必要技术术语可保留英文，不堆砌逐行翻译。

按项目语言实施自动检查，人工审查准确性和充分性；不要声称中文字符串存在即可证明中文注释合格，明确第三方/自动生成代码范围。

## 需求、业务与架构（按需求建立）

需求说明列角色、用例、业务规则、状态流程、边界、非目标、验收及未决项。经营公式、权限和历史数据变更需负责人确认，保留原因、影响与回滚证据。

架构说明列组件职责、数据流、依赖和决策理由；接口写参数、类型、单位、异常、授权、兼容规则；没有接口/数据库等需求不创建空文档。

## 数据、安全与运行（按风险建立）

数据库存在时明确 schema、迁移、事务/一致性、审计、历史数据处理、备份、恢复和演练。只提交结构、虚构/脱敏样例，不提交生产数据和真实凭据。

安全规范和 SECURITY.md 说明 S0/S1/S2 的判断、身份认证、资源授权、密钥外置、失败默认拒绝、日志脱敏、轮换及事件处理；具体高风险功能补越权/失效测试。

有部署需求时说明环境隔离、配置、构建、健康检查、升级和回滚；桌面程序说明安装及窗口/后台生命周期。部署流程文档不等于获得生产操作授权。

## 测试、CI 与完成定义

覆盖正常、异常、边界、核心业务回归及适用安全测试。根据语言加入格式、静态检查、单元/集成/端到端测试，不无依据承诺覆盖率或性能数字。

密钥扫描与必要 CI 必须实际运行并通过，记录 Commit 对应证据；失败、取消、跳过、待运行不冒充成功。Action 最小权限和不可变版本引用按安全规范维护。

确认当前账号能访问新仓库、检查能运行；平台不支持的保护如实记录，不公开仓库或付费绕过。保持 main 稳定，临时分支经 PR 和适用验收合并；版本和 Tag 仅对应真实发布。

## 变更记录与交付

CHANGELOG 记录变更、原因、影响、数据与兼容；VERSION 或其他唯一版本来源与 README/界面/Tag 一致。治理版本和产品版本分开，不为创建规则假造产品版本。

每次交付列项目分类与依据、仓库/路径、规则版本、实际变更、中文注释核查、测试与未覆盖项、扫描、Commit、PR、CI、main、适用 Tag、临时分支清理和回滚。

最终复核：旧仓库名称/路径/技术栈引用是否确有必要；文档与目录是否匹配；模板占位是否已消除或明确未决；自动检查是否适用于本项目，而不是机械继承 small-tools 或 OUTsoft 的目录校验器。
