# 认证、授权与密钥管理规范

**Security Standard Version: v1.0.0**  
**适配 Repository Standard: v1.1.0**  
**生效日期：2026-09-22**  
**状态：正式生效**

本规范适用于 `small-tools` 仓库内所有软件。它是 [REPO_STANDARD.md](REPO_STANDARD.md) 的专项规则；发生冲突时，以仓库主规则和更严格的安全要求为准。

## 1. 先判断安全级别

| 级别 | 判断条件 | 必须做到 |
|---|---|---|
| S0 | 纯本地、单用户、无账号、无外部密钥 | README 明确“不需要认证”；不保存敏感业务数据 |
| S1 | 使用 API Key、数据库密码、云服务或第三方账号 | 凭证外置、最小权限、失败即停止、秘密扫描、日志脱敏 |
| S2 | 多用户、联网服务、后台管理、远程访问或敏感数据 | 完整身份认证、权限控制、Token 生命周期、审计、限流和越权测试 |

无法判断时，按更高一级执行。一个工具从本地单机改为联网或多人使用时，必须重新评估。

## 2. 基本概念

- **认证（Authentication）**：确认“是谁”。
- **授权（Authorization）**：确认“这个身份能做什么”。
- **凭证（Credential）**：密码、API Key、Cookie、私钥、Token 等可用于证明身份的材料。
- **Access Token**：短期访问凭证，应限制有效期、范围和对象。
- **Refresh Token**：用于换取新 Access Token，风险更高，只能保存在受控服务端。

认证成功不等于拥有全部权限。所有敏感操作必须再次做资源级和动作级授权。

## 3. 责任分工

| 角色 | 责任 |
|---|---|
| 负责人 | 批准接入的外部系统、权限范围、生产凭证使用和高风险例外 |
| 开发人员 | 不索取不必要的真实凭证；按规范实现认证授权；补齐测试和文档 |
| 部署/运维人员 | 在运行环境注入凭证；控制读取权限；负责轮换、撤销和备份 |
| 审核人员 | 检查权限边界、日志脱敏、秘密扫描和回滚方案 |

## 4. 标准请求流程

### 4.1 入站用户请求（S2）

~~~text
客户端通过 TLS 发起请求
→ 认证入口提取 Session / Authorization
→ 校验签名、签发方、受众、有效期和撤销状态
→ 得到稳定用户身份
→ 按角色、动作和目标资源进行授权
→ 执行业务逻辑
→ 写入不含凭证的安全审计记录
~~~

任何一步失败都应默认拒绝。禁止因异常、超时或依赖故障自动放行。

### 4.2 调用外部 API（S1/S2）

~~~text
部署环境或密钥服务注入凭证
→ 应用启动时读取并校验必要配置
→ API 客户端在请求 Header 中携带凭证
→ 第三方服务返回结果
→ 日志只记录状态、请求标识和脱敏错误
~~~

API Key 和 Token 不得放在 URL 查询参数中。缺少必要凭证时应安全失败并给出不含敏感值的错误。

## 5. 凭证存储与注入

### 5.1 开发环境

- 只提交 `.env.example`，值留空或使用明显占位符。
- 真实 `.env`、证书、私钥、账号导出文件不得提交。
- 优先使用操作系统钥匙串、开发环境 Secret 或本地环境变量。
- Issue、PR、聊天、截图和测试样例中不得出现真实值。

Python 示例：

~~~python
import os

api_key = os.getenv("EXTERNAL_API_KEY")
if not api_key:
    raise RuntimeError("缺少 EXTERNAL_API_KEY 配置")
~~~

### 5.2 CI/CD

- 使用 GitHub Actions Secrets、Environment Secrets 或云平台 Secret。
- 工作流仅授予完成任务所需的最小 `GITHUB_TOKEN` 权限。
- 优先使用 OIDC 短期身份访问云资源，减少长期 Access Key。
- 不向不受信任的 Fork PR 暴露生产 Secret。
- 第三方 Action 固定到不可变提交 SHA，并由 Dependabot维护更新。

### 5.3 生产环境

- 使用平台 Secret Manager、受控环境变量或等效密钥服务。
- 生产和测试使用不同凭证、不同权限和不同数据。
- 有权限读取 Secret 的人员和服务必须最少化，并保留访问审计。
- 持久保存 Refresh Token 或私钥时，应使用受控密钥进行静态加密。

## 6. Token 生命周期

所有 Token 必须明确：签发方、使用方、权限范围、有效期、存储位置、轮换人和撤销方式。

- Access Token 应短期有效并使用最小 Scope。
- Refresh Token 只保存在服务端，禁止下发给不受控客户端或写入日志。
- 用户退出、密码重置、员工离职、权限变更和疑似泄露时，应能够撤销相关 Session/Token。
- 长期 API Key 必须有轮换计划；不用的凭证立即删除。
- 轮换时允许短暂双密钥过渡，但必须设置旧密钥失效时间。
- 不得自行设计加密算法、签名格式或 Token 协议。

## 7. 登录、密码与 Session

仅 S2 项目适用：

- 优先使用成熟身份服务或框架认证模块。
- 密码只能使用 Argon2id、bcrypt 或框架认可的密码哈希方案，不得明文或可逆加密保存。
- 登录接口必须有限流；后台和高权限账号应启用多因素认证。
- Session Cookie 至少设置 `HttpOnly`、`Secure` 和合适的 `SameSite`。
- 使用 Cookie 身份时必须处理 CSRF；修改密码、付款、导出等高风险动作应重新验证。
- 登录错误提示避免暴露账号是否存在。

## 8. OAuth、JWT 与 API Key

### OAuth

- 使用 `state` 防止请求伪造；公共客户端按协议使用 PKCE。
- Client Secret 和 Refresh Token 只放在服务端。
- 回调地址使用精确白名单，不允许任意跳转。

### JWT

- 必须校验签名算法、签发方、受众、有效期和生效时间。
- 禁止接受 `none` 算法或仅解码不验签。
- JWT 不是加密容器，不得写入密码、完整个人信息或其他敏感明文。

### API Key

- 通过 Header 传递，不放入 URL、文件名或命令行参数。
- 服务端只保存必要形式；可哈希比对时不保存明文。
- 每个系统、环境和用途使用独立 Key，便于审计和撤销。

## 9. 授权规则

- 默认拒绝，明确允许。
- 服务端必须执行授权，不能依赖前端隐藏按钮。
- 同时检查角色权限和目标资源归属，防止横向越权。
- 管理员、导出、删除、金额修改、批量操作等高风险能力单独授权。
- 禁止共享管理员账号；人员离职或岗位变化时及时回收权限。

## 10. 日志与错误处理

日志不得记录：

- Authorization Header、Cookie、密码、验证码；
- Access Token、Refresh Token、API Key、私钥；
- 完整数据库连接串；
- 含敏感字段的请求体和响应体；
- 可直接恢复真实凭证的哈希或编码结果。

建议记录：时间、动作、脱敏身份、结果、目标资源标识、请求 ID 和错误类别。需要展示凭证时，最多显示不可用于认证的短前后缀。

## 11. 测试要求

S1 至少测试：

- 缺少、错误、过期或被撤销凭证时安全失败；
- 日志和报错不包含凭证；
- 测试与生产配置隔离。

S2 还必须测试：

- 未登录、过期 Session、退出后的访问；
- 普通用户访问管理员功能；
- 用户访问其他用户资源；
- Token 篡改、错误签发方和错误受众；
- 登录限流、CSRF、重放和高风险操作验证。

测试只使用虚构凭证和脱敏数据。

## 12. Git 与自动检查

- `.gitignore` 是辅助措施，不代表文件一定安全；已经跟踪的文件不会因新增忽略规则而消失。
- `.github/workflows/secret-scan.yml` 在 PR 和 main 推送时扫描完整历史。
- 扫描失败必须先查明原因；不得用宽泛排除绕过。
- GitHub 设置支持时，应同时开启 Secret Scanning、Push Protection 和分支保护。
- 凭证一旦进入历史，先撤销/轮换，再考虑历史清理。

## 13. 安全事件

发现漏洞或泄密时按根目录 [SECURITY.md](../SECURITY.md) 执行。首要目标是停止继续损失和撤销访问能力，而不是先删除记录或追责。

## 14. 完成标准

项目只有满足以下适用项，才可标记完成：

- [ ] 已确定并记录 S0/S1/S2；
- [ ] 认证和授权边界已写入 README；
- [ ] 真实凭证均在 Git 外注入；
- [ ] Token 有有效期、轮换和撤销方案；
- [ ] 日志与错误已脱敏；
- [ ] 正常、失败、过期和越权场景已测试；
- [ ] 自动秘密扫描通过；
- [ ] 已说明未覆盖风险和回滚方式。
