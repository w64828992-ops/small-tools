# small-tools 开发、版本与归档主规则

**Rule Version: v1.3.0**  
**生效日期：2026-09-22**  
**规则状态：正式生效**

本文件是 `small-tools` 仓库的**唯一完整主规则**。根目录 README、模板和各软件文档必须与本文件保持一致。如其他文档与本文件冲突，以本文件为准。认证、授权、凭证和 Token 的具体执行要求见 `docs/AUTH_AND_SECRETS_STANDARD.md`；该文件是本主规则的专项细则。

---

## 1. 仓库定位

`small-tools` 不是临时代码堆放区，而是长期软件资产库。

任何进入仓库并持续维护的软件，都应尽量满足：

1. 能看懂：后来的人可以理解代码和业务规则。
2. 能运行：文档足以说明如何安装和启动。
3. 能追溯：知道当前版本、历史改动和改动原因。
4. 能维护：目录、配置、依赖和代码结构清晰。
5. 能验证：核心功能有测试或明确的校验方法。
6. 能回退：稳定版本可以定位和恢复。

---

## 2. 根目录规则：一个软件一个一级目录

仓库**不提前建立业务分类目录**。

禁止为了“以后可能会用”而预建：

```text
foreign-trade/
sales/
factory/
management/
...
```

需要开发一个新软件时，再建立一个新的一级目录：

```text
small-tools/
├── README.md
├── CHANGELOG.md
├── .gitignore
├── docs/
├── _templates/
├── quotation-calculator/
├── excel-cleaner/
└── image-compressor/
```

原则：

> 一个软件 = 一个一级目录。

同一个软件的代码、文档、版本信息、测试和配置说明尽量放在该目录内。

---

## 3. 软件目录规则

正式或持续维护的软件原则上至少包含：

```text
software-name/
├── README.md
├── CHANGELOG.md
├── VERSION
└── 源代码
```

按实际复杂度增加：

```text
src/                 # 主程序代码
tests/               # 自动化或人工测试
docs/                # 详细技术/业务文档
examples/            # 示例输入输出
config/              # 非敏感配置
data/                # 本地工作数据，通常不提交
output/              # 导出结果，通常不提交
logs/                # 日志，通常不提交
.env.example         # 环境变量示例，不放真实密钥
requirements.txt     # Python 依赖
package.json         # Node 依赖
```

不要机械创建空目录。目录必须服务于实际维护需要。

非常简单、一次性、只有少量代码的工具，可暂时只保留：

```text
README.md
VERSION
源代码
```

一旦开始持续维护，必须增加 `CHANGELOG.md`。

## 4. 命名规则

软件目录统一采用：

```text
英文小写 + 连字符
```

推荐：

```text
quotation-profit-calculator
excel-batch-renamer
customer-followup-helper
```

禁止用文件名表达版本状态：

```text
最终版
最新版
final2
new
new2
test3
修改版
```

版本只能通过正式版本号管理。

## 5. 版本管理规则

所有持续维护的软件使用：

```text
MAJOR.MINOR.PATCH
```

例如：

```text
0.1.0
0.4.2
1.0.0
1.3.0
1.3.1
2.0.0
```

### 5.1 PATCH

用于：

- Bug 修复
- 文案或显示小调整
- 不改变主要功能和接口的小改动

例如：

```text
1.3.0 → 1.3.1
```

### 5.2 MINOR

用于：

- 新增功能
- 新增兼容能力
- 对旧使用方式基本兼容的升级

例如：

```text
1.3.1 → 1.4.0
```

### 5.3 MAJOR

用于：

- 重大结构改版
- 关键接口不兼容
- 核心业务口径发生重大变化
- 数据结构或使用方式产生明显破坏性变化

例如：

```text
1.4.0 → 2.0.0
```

### 5.4 开发阶段

未达到稳定使用状态时使用：

```text
0.x.x
```

稳定投入长期使用后进入：

```text
1.0.0
```

### 5.5 每次修改都必须判断版本

每完成一轮可交付修改，都必须判断：

> 是否需要升级版本号？

不能长期修改功能却保持版本号不变。

## 6. 版本一致性规则

同一个正式版本的以下位置必须一致：

- `VERSION`
- README 中的当前版本
- CHANGELOG 中的版本记录
- 软件界面中的版本号（有界面的软件）
- 对应 Git Tag（已建立 Tag 时）

例如当前版本为 `1.4.2`，不能出现：

- VERSION = 1.4.2
- README = 1.4.0
- 软件界面 = 1.3.5

有界面的软件原则上应显示当前版本号，方便截图、排错和现场确认。

## 7. 代码注释是强制质量要求

代码不能只做到“能运行”，还要做到“后来的人看得懂为什么这样写”。

### 7.1 核心文件说明

核心代码文件开头应说明：

- 文件用途
- 主要职责
- 核心模块
- 关键依赖
- 修改注意事项
- 重要业务规则入口

示例：

```python
"""
文件：profit_calculator.py

用途：
计算订单报价、完整成本、毛利润和毛利率。

主要职责：
1. 汇总产品成本。
2. 加入包装和物流成本。
3. 计算利润。
4. 输出利润率。

注意：
利润口径属于核心业务规则。
修改利润公式前必须同步检查 README、CHANGELOG 和测试。
"""
```

### 7.2 重要函数说明

重要函数应说明：

- 功能
- 输入参数
- 参数单位
- 返回值
- 可能异常
- 业务规则
- 特殊边界
- 必要时增加示例

### 7.3 注释重点解释“为什么”

推荐：

```python
# 使用销售额作为毛利率分母，
# 因为当前经营分析统一使用销售毛利率口径：
# 毛利率 = 毛利润 / 销售额。
margin = profit / selling_price
```

不推荐：

```python
# 利润除以销售额
margin = profit / selling_price
```

### 7.4 禁止机械垃圾注释

不要求每一行都写注释。

例如：

```python
# a 加 1
a = a + 1
```

这类注释没有维护价值。

主原则：

> 复杂、关键、业务相关、容易误解、容易误改的地方必须详细注释；简单代码不制造无意义噪音。

## 9. README 文档标准

每个持续维护的软件必须拥有自己的 README。

README 的合格标准不是“存在”，而是：

> 一个没有参与开发的人，只看 README，就基本知道它是什么、怎么运行、怎么维护。

至少包含：

1. 软件名称
2. 当前版本
3. 遵循的 Repository Standard 版本
4. 软件用途
5. 解决的业务问题
6. 使用对象
7. 主要功能
8. 适用场景
9. 不适用场景
10. 安装方式
11. 启动方式
12. 输入说明
13. 输出说明
14. 数据字段和单位
15. 核心业务规则
16. 文件结构
17. 配置说明
18. 依赖说明
19. 使用示例
20. 注意事项
21. 已知问题
22. 已知限制
23. CHANGELOG 入口

复杂软件还应按需要增加：

- 系统架构
- API 文档
- 数据库结构
- 部署说明
- 数据备份/恢复
- 权限说明
- 异常处理说明

## 10. 业务规则必须文档化

关键业务公式和判断逻辑不能只存在代码中。

例如：

```text
毛利润 = 成交金额 - 产品成本 - 包装成本 - 运输成本
毛利率 = 毛利润 / 成交金额
```

应明确写入 README 或软件的 docs。

特别是以下规则：

- 利润
- 成本
- 报价
- 汇率
- 库存
- 交期
- 佣金
- 客户等级
- 绩效
- 订单状态

原因：

> 以后最容易产生争议的往往不是代码有没有运行，而是“当时到底按照什么经营口径计算”。

## 11. CHANGELOG 更新规则

持续维护的软件必须有 `CHANGELOG.md`。

每个正式版本至少记录：

- 版本号
- 发布日期
- 新增
- 修改
- 修复
- 删除（如有）
- 影响范围
- 数据影响
- 兼容性
- 注意事项

推荐格式：

```markdown
## v1.4.0 - 2026-09-19

### 新增
- 增加海运费自动分摊功能。

### 修改
- 利润计算加入包装费。

### 修复
- 修复订单数量为 0 时程序报错。

### 影响范围
- 利润计算模块
- 报价结果页面

### 数据影响
- 历史订单不自动重新计算。

### 兼容性
- 原输入文件格式保持兼容。

### 注意事项
- v1.4.0 与 v1.3.x 的利润口径不同。
```

禁止仅写：

```text
修复BUG
优化代码
更新程序
```

必须说明到底改了什么。

## 12. 核心业务逻辑修改规则

技术优化不能擅自改变经营规则。

以下内容发生变化时属于重点变更：

- 利润公式
- 成本口径
- 报价算法
- 库存扣减
- 交期判断
- 客户等级
- 佣金
- 绩效
- 订单状态
- 关键审批/权限

重大变更应记录：

1. 修改前是什么。
2. 存在什么问题。
3. 为什么修改。
4. 修改后是什么。
5. 影响哪些功能。
6. 是否影响历史数据。
7. 是否兼容旧版本。
8. 如何回滚。

如果变化会影响实际经营结果，应先向负责人说明并获得确认，再实施。

不改变业务结果的重构、命名优化、性能优化和异常处理可正常执行。

## 13. 测试规则

“代码写完”不等于“软件完成”。

正式交付流程：

```text
代码完成
→ 基础测试
→ 异常输入测试
→ 边界条件测试
→ 核心业务结果核对
→ README 检查
→ CHANGELOG 更新
→ VERSION 检查
→ 敏感信息检查
→ GitHub 提交
→ 交付摘要
```

计算类工具应重点检查：

- 正常值
- 0
- 空值
- 负数
- 极大值
- 极小值
- 小数
- 错误格式
- 除 0
- 币种
- 单位
- 舍入精度

交付时必须说明：

- 测试了什么
- 哪些通过
- 哪些没有覆盖
- 是否存在已知问题

---

### 13.1 扫描必须有可验证运行结果

自动安全检查的“配置存在”不等于“检查已执行”。

正式交付或合并时必须能确认：
- 对应 PR 或目标 Commit 确实产生了 Secret Scan / CI 运行记录；
- 运行结果为通过；
- 如工作流没有触发、Actions 被禁用、权限不足或状态无法读取，不得写“扫描通过”；
- 可先执行额外本地敏感信息检查作为补充，但本地检查不能冒充 GitHub 自动扫描；
- 应继续排查并恢复自动扫描能力，再把“自动扫描通过”勾选为完成。

---

## 14. 安全规则：代码可以上传，真实钥匙默认不上传

### 14.1 可以正常上传

- 源代码
- README
- 业务规则
- 计算公式
- 配置结构
- 数据库结构
- API 接口说明
- 测试代码
- 虚构测试数据
- 脱敏数据
- `.env.example`

### 14.2 默认不上传的“真实钥匙”

- 密码
- API Key
- Token
- Cookie
- 私钥
- SSH Key
- 数据库真实密码
- OAuth Refresh Token
- 云服务器 Access Key
- 其他能直接授权访问系统或产生费用的凭证

允许上传：

```text
OPENAI_API_KEY=your_key_here
```

默认不上传：

```text
OPENAI_API_KEY=真实密钥
```

原因不是 GitHub 不能保存，而是 Git 会长期保留历史；一旦凭证曾进入历史，后续简单删除并不等于真正消除风险。

### 14.3 不允许以例外方式提交明文凭证

即使负责人因特殊业务提出要求，也不得把明文真实凭证提交进 Git。应改用 GitHub Actions Secrets、部署平台 Secret、环境变量或专用密钥服务。

如必须随项目保存加密材料，解密密钥必须存放在仓库之外，并由负责人确认访问范围、轮换和应急方案。Base64、压缩包、改后缀不属于加密。

## 15. 真实业务数据规则

GitHub 主要用于管理软件资产，不作为默认业务数据库。

以下真实数据原则上不和源代码混放：

- 客户名单和联系方式
- 真实订单
- 供应商底价
- 员工个人信息
- 账号信息
- 未脱敏经营数据
- 其他敏感内部资料

开发和测试优先使用：

- 虚构数据
- 脱敏数据
- 最小必要样例

如果某个软件确实需要将真实业务文件放入仓库，应由负责人明确确认具体文件和用途。

---

## 16. 配置、数据、日志与代码分离

真实凭证必须通过环境变量、部署平台 Secret、操作系统钥匙串或专用密钥服务注入。生产环境不得依赖仓库内的本地配置文件保存真实凭证。

推荐：

```python
api_key = os.getenv("OPENAI_API_KEY")
```

不推荐：

```python
api_key = "真实密钥"
```

复杂软件按需要分离：

```text
src/       程序代码
config/    非敏感配置
data/      工作数据
output/    导出文件
logs/      日志
```

`data/`、`output/`、`logs/` 是否进入 Git，按项目实际需要决定；大量运行数据和临时输出通常不提交。

日志不得记录密码、Token、Cookie、Authorization Header、私钥或完整数据库连接串。需要排错时只记录请求标识、状态、错误类别和不可用于认证的脱敏信息。

## 17. Git 提交规则

禁止使用缺乏信息的提交说明：

```text
update
修改
new
final
fix
```

推荐：

```text
<type>(software-name): <明确说明>
```

常用类型：

- `feat`：新增功能
- `fix`：修复
- `docs`：文档
- `refactor`：重构
- `test`：测试
- `chore`：维护
- `release`：正式版本

示例：

```text
feat(quotation-tool): add freight allocation
fix(quotation-tool): correct profit calculation
docs(quotation-tool): update v1.4.0 usage guide
release(quotation-tool): v1.4.0
```

一次提交尽量对应一类明确变化。

## 18. 稳定版本与回滚

重要正式版本建议创建 Git Tag。

推荐命名：

```text
software-name-v1.0.0
software-name-v1.2.0
software-name-v2.0.0
```

目标：

> 新版本出现严重问题时，可以明确找到上一个稳定状态。

---

## 19. 禁止“偷偷改需求”

开发过程中如果发现：

- 原需求逻辑存在问题
- 某个业务公式可能不合理
- 有更好的实现方式

可以提出建议，但不得未经确认擅自改变重要业务结果。

以下优化在不改变业务结果时可以正常实施：

- 代码重构
- 性能优化
- 命名优化
- 注释补充
- 异常处理
- 测试完善

## 21. 主规则自身版本化

本规则也使用语义化版本。

例如：

```text
v1.0.0 → v1.1.0
```

用于新增兼容规则。

重大治理方式变化可升级：

```text
v1.x.x → v2.0.0
```

每次规则更新必须记录：

- 改了什么
- 为什么改
- 什么时候生效
- 影响哪些软件
- 旧软件如何处理

## 22. 主规则唯一权威来源

唯一完整规则文件：

```text
docs/REPO_STANDARD.md
```

其他文件职责：

- 根 README：规则摘要 + 仓库入口。
- `_templates/`：落实规则的模板。
- 根 CHANGELOG：记录仓库治理变化。
- 软件 README/CHANGELOG：记录单个软件。

如果出现冲突，以 `docs/REPO_STANDARD.md` 为准。

---

## 23. 规则更新同步机制

任何主规则更新后，必须同步检查：

1. `docs/REPO_STANDARD.md`
2. 根 `README.md`
3. `_templates/`
4. 根 `CHANGELOG.md`
5. 被新规则影响的已有软件

执行原则：

- 新软件：立即执行最新规则。
- 正在修改的旧软件：本次修改时同步检查适配。
- 重要旧软件：如规则变化涉及质量、安全或版本治理，可主动升级。
- 不要求为了形式一次性重写所有历史代码，但必须明确其遵循的规则版本。

---

## 24. 每个软件记录遵循的规则版本

软件 README 中应标记：

```text
Repository Standard: v1.3.0
```

这样未来规则升级后，可以判断旧软件是否需要升级规范。

## 25. 完成标准（Definition of Done）

一个正式软件或正式版本只有在关键项目满足后，才可标记“已完成”：

- [ ] 核心功能正常
- [ ] 核心业务逻辑已核对
- [ ] 重要代码有详细、有价值的注释
- [ ] README 已更新
- [ ] 业务规则已文档化
- [ ] VERSION 正确
- [ ] CHANGELOG 已更新
- [ ] 核心测试通过
- [ ] 已说明未覆盖测试
- [ ] 已确定 S0/S1/S2 安全级别
- [ ] 认证、授权和凭证处理符合专项规范（适用时）
- [ ] 未意外提交真实密码、Token、API Key 等凭证
- [ ] 自动敏感信息扫描**实际产生运行记录并通过**；仅存在 workflow 文件或“未返回状态”都不能视为通过
- [ ] Git 提交说明清楚
- [ ] 代码已备份 GitHub
- [ ] 已输出交付摘要

未满足关键条件时，应明确标记：

- 开发中
- 待测试
- 待文档
- 待确认

不能直接宣称“已完成”。

## 26. 默认开发协助责任

以后负责人只需要提出要开发或修改什么软件，不需要每次重复本规则。

默认开发流程包括：

1. 读取当前软件 README、VERSION、CHANGELOG 和相关代码。
2. 理解现有业务规则和版本状态。
3. 判断 S0/S1/S2 安全级别及适用要求。
4. 新建或调整代码。
5. 对核心代码补充详细注释。
6. 实现必要的认证、授权、凭证和日志保护。
7. 添加或执行正常、异常、边界和越权测试。
8. 更新 README。
9. 更新 CHANGELOG。
10. 判断并更新版本号。
11. 执行敏感信息检查和自动扫描。
12. 提交 GitHub。
13. 给出交付摘要。

## 27. 十条核心原则

1. **一个软件一个目录。**
2. **一个版本一个完整状态。**
3. **代码必须看得懂。**
4. **业务规则不能只存在代码里。**
5. **每次修改必须留下记录。**
6. **重要版本必须可以回退。**
7. **代码可以进 GitHub，真实钥匙绝不进 Git。**
8. **认证与授权默认拒绝、最小权限。**
9. **自动安全扫描失败不得绕过。**
10. **规则变化，文档、模板和软件同步执行。**

## 28. 认证与密钥管理专项规则

所有软件必须先按下列级别判断安全要求：

- `S0`：本地单机、无账号、无外部凭证。
- `S1`：使用 API Key、数据库、云服务或其他外部凭证。
- `S2`：多用户、联网服务、后台管理、远程访问或处理敏感数据。

无法判断时按更高一级执行。完整请求流程、凭证注入、Token 生命周期、登录与 Session、OAuth/JWT、日志脱敏、测试和应急要求，以 `docs/AUTH_AND_SECRETS_STANDARD.md` 为准。

发现漏洞或凭证误提交时，必须按根目录 `SECURITY.md` 处置：先撤销或轮换，再检查影响和清理历史。

## 29. 桌面可执行工具与后台服务规则

适用于 macOS App、Windows 桌面程序、菜单栏工具、托盘程序，以及会控制后台进程、LaunchAgent、Service、Daemon 的本地工具。

### 29.1 源码必须可复现构建

桌面工具不能只上传可执行文件。仓库至少应保留：

- 可读源码；
- 明确版本号；
- 构建方法；
- 安装或部署方法；
- 依赖与系统要求；
- 最小验证方式。

如图标、plist、manifest 等产物可以由脚本稳定生成，优先保留生成逻辑，减少不透明二进制文件。

### 29.2 源码、构建产物与当前正式版本必须对应

交付前必须确认：

- VERSION 与界面版本一致；
- GitHub 源码能重新编译出同一功能版本；
- 本机当前正式运行版本来自同一份源码或明确记录的 Commit/Tag；
- 不允许只在本机临时修改，却没有回写仓库。

### 29.3 安装行为与运行行为分离

安装脚本原则上只负责安装、注册和必要文件复制。

除非产品需求明确要求，否则安装过程不得自动：

- 开启远程访问；
- 启动高风险后台服务；
- 修改业务数据；
- 删除旧数据；
- 改变当前用户正在使用的连接状态。

### 29.4 窗口生命周期与后台服务生命周期必须写清

如果桌面界面控制独立后台服务，必须明确说明：

- 打开窗口是否自动启动服务；
- 关闭窗口是否停止服务；
- 退出 App 是否停止服务；
- 用户通过什么动作才真正启停服务；
- 下次打开界面时如何读取真实状态。

禁止把“窗口关闭”和“后台服务停止”默认视为同一件事。

### 29.5 状态显示必须以真实系统状态为准

界面中的“已连接 / 已启动 / 已停止”等状态，不能只依赖 UI 内存或上一次点击结果。

应尽量通过系统、进程、端口、服务管理器或实际健康检查重新读取真实状态。

### 29.6 高风险后台控制必须默认安全测试

涉及远程访问、网络代理、数据库、生产服务等高风险后台能力时：

- 自动测试默认不得主动切断当前关键连接；
- destructive / live-toggle 测试必须显式 opt-in；
- 测试脚本必须明显提示会改变真实运行状态；
- 远程会话中不得为了“测试完整”而主动切断自身控制链路，除非有独立恢复通道。

### 29.7 桌面工具交付最小文件

持续维护的桌面工具建议至少包含：

```text
software-name/
├── README.md
├── CHANGELOG.md
├── VERSION
├── src/
├── scripts/
│   ├── build.*
│   └── install.*
├── tests/
└── docs/
```

简单工具可按实际情况删减，但“源码 + 版本 + 构建 + 使用 + 验证”五项不得缺失。

## 30. 分支与小工具长期维护规则

本仓库采用“`main` 为唯一正式源 + 每个小工具一个稳定入口分支 + 临时开发分支短期存在”的方式管理。

### 30.1 main 是唯一正式代码源

`main` 代表仓库当前正式状态。所有已经验收、可交付、可恢复的小工具最终都必须进入 `main`。

禁止让某个小工具长期只存在于独立分支而不进入 `main`。恢复、交接、审计和重新构建时，默认优先以 `main` 为准。

### 30.2 每个小工具建立一个长期稳定入口分支

每个持续维护的软件建立：

```text
tool/<software-name>
```

例如：

```text
tool/drc-control-switch
```

该分支的职责是指向该工具当前已确认的稳定状态，便于快速定位、继续开发和交接。

注意：Git 分支包含整个仓库快照，不是文件夹。因此 `tool/drc-control-switch` 中看到其他仓库文件属于正常现象，不代表源码重复。

### 30.3 tool 分支不得成为独立主线

`tool/*` 不作为长期独立开发主线，不允许与 `main` 长期分叉。

正式版本发布后，应将对应 `tool/*` 分支同步到该工具已进入 `main` 的稳定提交。

### 30.4 临时开发分支命名

新增功能：

```text
feat/<software-name>/<short-description>
```

Bug 修复：

```text
fix/<software-name>/<short-description>
```

仓库规范或文档：

```text
docs/<short-description>
```

安全修复：

```text
security/<software-name>/<short-description>
```

禁止同时混用 `feat/` 与 `feature/` 等重复前缀。

### 30.5 临时分支生命周期

标准流程：

```text
从 main 创建临时分支
→ 开发
→ 测试
→ 文档/版本检查
→ PR
→ 合并 main
→ 同步对应 tool/* 稳定分支
→ 删除临时分支
```

临时 `feat/*`、`fix/*`、`docs/*`、`security/*` 分支合并后原则上必须删除，避免形成“看起来像正式版本但实际已过期”的分支。

### 30.6 正式版本使用 Tag，而不是版本分支

正式版本使用不可变 Tag：

```text
<software-name>-vMAJOR.MINOR.PATCH
```

例如：

```text
drc-control-switch-v1.0.0
```

禁止用以下方式长期保存版本：

```text
feature/drc-control-switch-v1.0.0
final-v1
latest
stable2
```

Tag 用于历史版本定位；`tool/*` 用于当前稳定入口；`main` 是唯一正式源。三者职责必须分开。

### 30.7 分支清理检查

每次正式交付后必须检查：

- 是否残留已合并临时分支；
- 是否存在同一软件多个含义重复的长期分支；
- `tool/*` 是否与当前稳定 `main` 提交一致；
- 是否存在名字像正式版本、但内容为空或过期的误导分支；
- 是否需要建立正式版本 Tag。

如 GitHub 工具权限不支持删除分支，必须明确记录“待物理删除”，不得宣称已经清理完成。

### 30.8 软件 README 记录两个规范版本

持续维护的软件 README 推荐同时记录：

```text
Release Standard: vX.Y.Z
Current Compatible Standard: vA.B.C
```

含义：

- **Release Standard**：该版本正式发布时实际遵循的仓库规范版本，作为历史记录，不随规范升级而改写。
- **Current Compatible Standard**：最近一次检查确认兼容的当前仓库规范版本，可随规范审查更新。

这样既保留历史真实性，又能判断旧工具是否适配当前治理要求。
