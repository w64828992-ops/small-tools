# small-tools 开发与归档规范

## 1. 核心原则

这个仓库不是“临时代码堆放区”，而是可长期维护的小工具资产库。

每次新增或修改工具，都要同时考虑：

- 能不能直接使用
- 能不能看懂
- 能不能继续修改
- 出问题能不能回滚
- 半年后还能不能知道它是干什么的

## 2. 分类规则

优先按业务用途分类，而不是按编程语言分类。

一个工具跨多个业务场景时，放到“主要使用场景”目录；真正通用的能力放到 `shared/` 或 `data-tools/`。

## 3. 单个工具建议结构

```text
category/tool-name/
├── README.md
├── src/
├── tests/            # 有逻辑判断时建议保留
├── examples/         # 示例输入输出
├── requirements.txt # Python 项目需要时
├── package.json      # Node 项目需要时
└── CHANGELOG.md      # 重要或长期维护工具建议保留
```

不要为了“看起来完整”创建无用目录。

## 4. README 必填信息

每个工具 README 至少写清：

- 工具名称
- 业务目的
- 使用对象
- 核心功能
- 使用方法
- 输入
- 输出
- 环境与依赖
- 注意事项
- 已知限制
- 最近重要变化

## 5. 代码要求

- 配置、账号、密码、Token 不得直接写入代码仓库。
- 密钥统一通过环境变量或本地配置文件读取。
- 本地敏感配置必须加入 `.gitignore`。
- 业务计算逻辑尽量与界面代码分离。
- 对金额、利润、报价、交期等关键逻辑，优先增加测试或校验样例。
- 工具输出必须尽量可追溯，避免“算出一个数但不知道怎么算的”。

## 6. 提交规范

提交信息格式：

```text
<type>: <简短说明>
```

常用 type：

- `feat`：新增功能
- `fix`：修复问题
- `docs`：文档修改
- `refactor`：重构
- `test`：测试
- `chore`：仓库维护

一次提交尽量只解决一类问题。

## 7. 版本与备份

重要工具建议使用语义化版本：

- MAJOR：不兼容的大改
- MINOR：兼容的新功能
- PATCH：兼容的问题修复

阶段性稳定版本可打 Git tag。

## 8. 新工具上线检查

上线前至少确认：

- [ ] 工具放对分类
- [ ] README 完整
- [ ] 无密码、Token、客户隐私等敏感信息
- [ ] 基础功能已验证
- [ ] 输入异常有基本处理
- [ ] 输出结果可理解
- [ ] 提交说明清楚
- [ ] 重要逻辑有示例或测试

## 9. 默认维护责任

以后由 ChatGPT 协助创建的小工具，默认遵守本规范；新增分类时，同时更新仓库根目录 README。
