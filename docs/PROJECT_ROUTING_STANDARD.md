# 本机软件规模判断与仓库分配规范

Routing Standard: v1.0.0
生效日期：2026-10-02
依据：负责人要求“本机开发的软件根据项目大小，小的软件到 small-tools，大软件单独建立仓库，并根据需求建立规则说明”。

## 1. 默认归属

| 项目类型 | GitHub 位置 | Windows 长期工作区 |
| --- | --- | --- |
| 小软件、小工具、范围清晰的自动化程序 | `w64828992-ops/small-tools` 内 `<software-name>/` | `D:\Dev\small-tools\<software-name>` |
| 大软件、复杂系统、需要独立治理的产品 | `w64828992-ops/<project-name>` 独立仓库 | `D:\Dev\<project-name>` |

small-tools 根目录允许共享治理规则和模板，不作为大项目业务代码存放区。独立仓库不嵌套到 small-tools 的工作区，不把 D:\Dev 整体初始化为 Git 仓库。

同一个项目只保留一个明确的正式源码仓库。修改现有项目时优先确认它现有的 remote 和文档，不因这条新规则擅自搬迁。用户明确指定的仓库或特殊范围优先于默认分配；与安全边界或实际权限冲突时说明问题。

## 2. 如何判断大小

由开发协助方根据实际需求判断并说明依据，不要求负责人反复选择，也不设置机械的代码行数、安装包体积或开发天数阈值。

小项目通常目标单一、功能边界清晰、模块耦合少、构建与发布相对简单，且无需独立团队权限或长期环境治理。例如批量改名、格式转换、单用途计算和小型桌面辅助程序；例子不是对现有项目的自动重新分类。

大项目通常存在多个业务域、复杂业务流程、持续的数据模型与迁移、前后端或多服务协同、长期运维及独立迭代需求。需要独立的访问权限、部署生命周期或发布管理时，即使原型代码很少，也应独立建仓。

仅使用数据库、调用 API、联网或带图形界面，不单独决定项目大小。安全级别 S0/S1/S2 与规模分别评估，小项目也不得降低认证、授权、数据保护和扫描要求。

边界项目综合功能范围、模块/依赖、数据复杂度、部署、协作与预计维护周期作出选择，把结论、依据和待确认需求写进项目说明。不能把未知需求假定为已确认，也不为了判断大小先搭空框架。

## 3. 开发前的落地步骤

1. 读取本规范、本机开发入口和目标项目已有 AGENTS/主规则；检查账号、remote、分支、未提交修改和已存在的同名项目。
2. 在项目 README 或 `docs/PROJECT_BRIEF.md` 记录项目名称、目标、范围/非目标、规模判断、仓库、本地路径、技术栈依据、安全级别、验收方式及未决问题。
3. 小项目按 small-tools 主规则建一级目录；大项目以项目专用名称建立独立私有仓库，不覆盖同名仓库、历史或本地目录。无明确名称时可提出并使用无冲突的描述性英文名，同时告知负责人。
4. 在权限允许且任务未禁止上传的情况下自动完成建仓、规范初始化和 GitHub 归档，无需再次询问常规分仓操作。权限不足则停止相应写入并说明，不能索取明文令牌或尝试绕过权限。
5. 新仓库默认私有。公开、付费升级、邀请协作者、选择开源许可证、访问生产环境及部署必须另有明确授权。

## 4. 小项目最低交付

遵循 small-tools 的主规则、安全与 Windows 工作流。持续维护的小项目至少有 README、CHANGELOG、VERSION、实际源码和与风险相称的测试；一个工具一个目录，正式代码进入 main，适用时维护 tool/<software-name> 与软件 Tag。

很小的项目可简化模块层次，但不能省略中文注释、必要测试、敏感信息检查、版本判断与实际归档证据。纯分析或临时实验的任务按用户指定范围执行，不假称已经发布。

## 5. 大项目按需求建立自己的规则

独立仓库的主规则必须写明本项目的名称、用途、边界、架构决策、目录、依赖、验证入口和发布方式。可参考已有仓库，但不能复制旧仓库名、固定路径、无关业务规则、过期命令或不适用的 CI。

基础文档：README.md、AGENTS.md、docs/REPO_STANDARD.md、docs/DEVELOPMENT_STANDARD.md、CHANGELOG.md、SECURITY.md，以及需求和验收说明。真实软件形成版本时建立 VERSION 或明确唯一版本来源；只有治理框架时不虚构软件版本、Tag 或测试结果。

根据实际需求补充：

- 多模块系统：架构、模块职责、接口契约、关键依赖与变更决策。
- 数据库或历史业务数据：数据模型、迁移、审计、备份、恢复、兼容及回滚。
- 多用户或联网功能：认证、授权矩阵、凭据外置、失败策略、日志脱敏与越权测试。
- 需要部署：环境隔离、构建、配置、健康检查、升级和回滚；不放真实密码。
- 桌面软件：可复现构建、安装方式、界面与后台生命周期、默认安全的运行验证。
- 性能或可用性约束：可测量目标、测试输入、指标采集和验收标准，不编造指标。

目录按软件需求选用 src、frontend、backend、tests、database、deployment 等，不要求每个目录都成为“单独软件”，也不预建用不到的目录。单产品通常使用 main、临时开发分支与 vMAJOR.MINOR.PATCH Tag，不机械复制 tool/*；组件独立发布时再明确组件版本方案。

先填写 `_templates/INDEPENDENT_PROJECT_STANDARD_TEMPLATE.md`，再生成实际文档和适配本项目的 CI。占位模板不能作为“需求已完成”或“测试通过”的证据。不能未经修改就把多工具仓库检查器用于单产品目录。

## 6. 不论大小都必须满足

所有自行编写、修改或持续维护的源码、脚本和测试都必须有中文注释：文件用途、类/具名函数/方法职责，关键业务逻辑、权限、数据操作与异常边界的原因及风险。注释与实现同步，不以中文业务字符串、机械翻译或过时说明充数；第三方或生成代码记录来源及例外，不修改以凑注释。

测试、README、CHANGELOG、版本判断、密钥扫描、临时分支、PR、当前提交的真实 CI 结果和交付记录均按项目适用性完成。没有中文注释、检查失败、无运行记录、仍在排队、未合并都不能写成已完成。没有语言自动检查器时逐文件人工核验，明确自动化覆盖边界。

需求和经营口径、权限、真实历史数据不得擅改；真实凭据和未脱敏业务数据不进 Git。不强推、不重写 Tag、不删除重要分支、不切断远程链路。默认归档不覆盖用户“仅分析/不上传/不合并”的限制。

## 7. 小项目增长与既有项目

发现小工具持续扩展为大项目时，先记录独立建仓建议、范围、来源 Commit、历史保留方式、调用依赖和迁移计划。实际迁移、删除旧代码或改动正式运行路径前确认；不能两处长期独立修改同一产品，也不能直接复制后删除原始历史。

本次规则只规范新项目分配和后续评估，不迁移、删除、改名现有 small-tools、huiyun-ems、OUTsoft 或其他软件，不改变业务技术栈及正式运行状态。OUTsoft 是已有独立仓库，不是所有新软件的默认容器；具体用途以其需求为准。

## 8. 持久化与交付记录

版本化来源为 `small-tools/docs/PROJECT_ROUTING_STANDARD.md`；本机入口为 `D:\Dev\AGENTS.md`，可由 `_templates/WORKSPACE_AGENTS_TEMPLATE.md` 恢复。各项目根 AGENTS 仍需明确分仓与项目范围；不同工具是否自动读取入口取决于工具本身，不能声称已强制控制所有开发工具。

分仓规范解决项目归属，目标仓库主规则解决具体实现和交付。既有项目流程不因外部文档更新被静默覆盖；改变现有项目结构或规则时提交对应 PR 并记录取舍。

交付记录至少包括：分类及依据、仓库与路径、规则版本、实际变更/验证、Commit、PR、CI、main、适用 Tag、临时分支状态与限制。规则更新同步本机入口、摘要和模板；历史软件 Release Standard 不追写新版本。
